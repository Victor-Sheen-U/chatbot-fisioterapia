Clase 07 · Conversación con historial

La clase pasada conectamos Groq con nuestra FastAPI. Hoy haremos que una pregunta pueda apoyarse en lo dicho antes. Quiero que veamos exactamente qué se guarda en messages[] y qué se vuelve a enviar en cada turno.

Los botones ejecutan Python y muestran el historial en esta misma pantalla. Comenzaremos con respuestas locales programadas para estudiar el mecanismo; al final podremos repetirlo con Groq.

¿Qué faltaba en la clase anterior?

Si enviamos «Me llamo Laura» y después enviamos solo «¿Cómo me llamo?», la segunda petición no lleva el nombre. El modelo no puede leer la terminal ni recuperar por sí solo una petición anterior de nuestro programa.

Una sola pregunta

Enviamos las instrucciones y la frase actual. La respuesta depende de ese contenido.

Conversación con historial

Enviamos las instrucciones, los turnos anteriores y la frase actual, en ese orden.

La memoria que construiremos hoy está en la lista de Python. El programa decide qué mensajes incluir en la siguiente petición.

FUNDAMENTO 1

Los roles de cada mensaje

Cada elemento de messages[] tiene un role y un content. system contiene las instrucciones; user, lo que escribe la persona; assistant, la respuesta. Guardar también la respuesta permite que el siguiente turno tenga el contexto completo.

{"role": "system", "content": "Responde en español"}
{"role": "user", "content": "¿Qué servicios tienen?"}
{"role": "assistant", "content": "Tenemos corte y barba"}

FUNDAMENTO 2

Empezamos con una lista

La conversación nueva comienza con el mensaje system. Todavía no hay preguntas ni respuestas. En cada turno agregaremos dos mensajes más: uno de user y uno de assistant.

def nuevo_historial():
    return [
        {"role": "system", "content": INSTRUCCIONES}
    ]

Pulsa el botón para iniciar. Si ya hiciste otras pruebas, también sirve para volver al comienzo.

FUNDAMENTO 3 · PRIMER TURNO

«Me llamo Laura»

Agregamos el mensaje de la persona a la lista. Después calculamos la respuesta local y añadimos un mensaje assistant. Quiero que observen el orden y cuántos elementos hay al terminar.

mensajes = historial + [
    {"role": "user", "content": "Me llamo Laura"}
]
mensajes += [
    {"role": "assistant", "content": respuesta}
]

Modo local: la respuesta la produce una función Python, no Groq.

FUNDAMENTO 4 · SEGUNDO TURNO

«¿Cómo me llamo?»

Ahora la función recibe el historial que quedó del turno anterior. Puede encontrar «Laura» en el mensaje previo de user. La respuesta nueva se agrega al final de la misma conversación.

mensajes_para_enviar = historial + [
    {"role": "user", "content": "¿Cómo me llamo?"}
]

Si no ejecutaste el primer turno, la función dirá que no conoce el nombre. Eso también es correcto.

COMPROBACIÓN

La misma pregunta sin historial

Vamos a enviar «¿Cómo me llamo?» en una conversación nueva. Allí solo estarán system y la pregunta actual. La función no podrá encontrar el nombre. Esta comparación muestra qué información aportó el historial.

sin_historial = [
    {"role": "system", "content": INSTRUCCIONES},
    {"role": "user", "content": "¿Cómo me llamo?"}
]

FUNDAMENTO 5

Qué enviamos en el siguiente turno

El historial conserva el orden completo. Cuando consultemos Groq, messages será esta lista más la pregunta nueva. El proveedor recibirá esos mensajes; no abrirá una base de datos ni buscará por su cuenta conversaciones anteriores.

payload = {
    "model": modelo,
    "messages": historial + [
        {"role": "user", "content": pregunta}
    ],
    "stream": False,
}

Cada turno completo añade un mensaje user y uno assistant.

FUNDAMENTO 6

La conversación y el negocio van por separado

El historial ayuda a interpretar lo que la persona quiere. No es el catálogo ni el archivo de reservas. Una función aparte consulta los datos del negocio. En los proyectos de los equipos, esa función seguirá llamando a la FastAPI.

def consultar_servicios():
    return negocio["servicios"]

# En consulta_llm.py:
# ejecutar(plan) llama a la ruta de FastAPI.

Esta demostración lee el catálogo de ejemplo. No cambia el historial de la conversación.

FUNDAMENTO 7

Si falla la petición, no guardamos una respuesta

Para consultar Groq necesitamos tanto la clave como el ID del modelo. Aquí provocaré un error de configuración antes de usar la red. Después consultaré la lista: el turno fallido no debe aparecer como una respuesta del asistente.

candidatos = historial + [mensaje_usuario]
respuesta = llamar_groq(candidatos)
# Solo si llegó correctamente:
historial = candidatos + [mensaje_asistente]

FUNDAMENTO 8

Reiniciar la conversación

Reiniciar significa crear otra lista con solo system. Ya no enviamos a Groq el nombre ni los turnos de la conversación anterior. Las reservas de FastAPI no se borran por reiniciar el chat: son datos del negocio, no historial.

historial = nuevo_historial()
# Resultado: un solo mensaje system.

Después vuelve a preguntar «¿Cómo me llamo?» en la diapositiva del segundo turno.
